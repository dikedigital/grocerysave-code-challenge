# Decision log

Choices made where TECH_SPEC left room (or where the product owner chose to depart from it), how
they were settled, and where they live in the code. Status:

- **Confirmed**: decided or approved by the product owner.
- **Deviation**: confirmed, and departs from the wording of TECH_SPEC or `src/models`. Re-check
  these if the spec is ever used as an acceptance test.
- **Proposed**: made during implementation where the spec is silent; awaiting the product owner's
  review.
- **Temporary**: a stop-gap until a later stage replaces it.
- **Withdrawn**: no longer applies; kept so that old references can be traced.

Code comments refer to these entries by id (for example `decision D-15`).

## Routing (`src/utils/route.ts`), stage 2

Spec: TECH_SPEC 5.5. `haversineKm` and `planRoute`: exact up to 8 stops (D-28), nearest
neighbour + 2-opt beyond (D-34 to D-36). Fixtures: `tests/fixtures/route.ts`; tests:
`src/utils/__tests__/route.test.ts`.

| Id | Decision | Why | Status |
|---|---|---|---|
| D-28 | **The tie rule, and the exact search.** Up to 8 stops, `planRoute` tries every visiting order (depth-first, positions taken in ascending input order, so orders come in lexicographic order of input positions) and replaces the best only when an order is *strictly* shorter. "Keeps the input sequence earliest" is read as: among equally short orders, the one whose sequence of input positions is lexicographically smallest. Examples: a round trip along a line keeps whichever direction the input lists first; stores at the same spot are visited back to back in input order. No pruning: all 255 subsets of the 8 seeded stores are routed in about 40 ms, far under the 2 s budget of 5.4. | Spec 5.5 says "equal-length orders (including the two directions along a line) keep the input sequence"; this is the natural reading that also gives one deterministic answer when more than two orders tie (from input `[b, a, c]` on a line, `b, c, a` is as short as `a, b, c`, and comes first). | **Confirmed** by the product owner (stage 2, third round): *"When two orders are equally short it should keep the input sequence, including the two directions along a straight line."* The rule is about complete **orders** and applies to all of `planRoute`, exact and heuristic (D-38). |
| D-29 | **Two lengths within 1e-9 km (1 micrometre) are equal** (`ROUTE_TIE_TOLERANCE_KM`). Leg distances are computed once per pair, so both directions of a leg are the same number. | A route and its reverse have the same length, but adding the legs in another order can differ in the last bit (seen in the fixture: `28.391702923807312` vs `...316`). Without the tolerance the tie rule of D-28 would be decided by float noise; removing it makes 3 tests fail. | Proposed |
| D-30 | **Invalid input throws a `RangeError`** instead of returning a plan: an origin or store location whose `lat` or `lng` is not a finite number (NaN, Infinity, missing, a string), or a `mode` other than `driving`/`walking` (inherited keys such as `toString` included). Latitude/longitude *ranges* are not checked by `planRoute` (haversine is well defined for any finite value). | Silently continuing would produce NaN distances, which `roundTo` turns into a believable `0 km` route (D-01). The HTTP layer must validate `origin` itself and answer 400 (spec 6.3, **Routes**: `POST /routes/optimize`), so this is a programming-error guard, not user-facing. | Proposed |
| D-31 | ~~More than 8 stops throws `not implemented`~~ (stage 2, first round). | Stop-gap while only the exact part existed. | **Superseded** by D-34 to D-36 (stage 2, second round) |
| D-32 | **Rounding.** `legDistanceKm` and `returnDistanceKm`: `roundTo(km, 2)`; `legDurationMin`: `roundTo(minutes, 0)` (half away from zero, drift-free, never `-0`). `totalDistanceKm` is the rounded sum of the unrounded legs including the return leg; `totalDurationMin` is computed from that unrounded total distance. ### Beyond 8 stops: nearest neighbour + 2-opt

D-34 and D-36 were withdrawn in the third round of stage 2: they weakened the tie rule of D-28 for
the heuristic. D-38 replaces them.

| Id | Decision | Why | Status |
|---|---|---|---|
| D-34 | ~~"Equally near stops are taken in input order" as the heuristic's version of the tie rule.~~ | It redefined the tie rule in terms of equally near **stops** instead of equally short **orders**, against D-28. Nearest neighbour still takes the earlier of two equally near stops, but only as a deterministic starting route; the tie rule is applied to complete orders (D-38). | **Withdrawn** (stage 2, third round) |
| D-35 | **2-opt**: a move reverses a run of consecutive stops. Step 1 applies every reversal that shortens the route by more than 1e-9 km, scanning (first, last) pairs in ascending order, in passes until none is left. Step 2 applies the equally short reversals that keep the input sequence better (D-38). Both steps repeat until neither changes anything. One way, a run that ends at the final stop has no following leg, so only its first leg changes ("2-opt also works one-way", spec 5.5). The result is never longer than nearest neighbour. **Termination**: an equally short move must keep the recomputed length within 1e-9 km of the shortest length seen so far and makes the order strictly earlier in input sequence; a shorter move lowers the shortest length seen; neither can go on forever over finitely many orders. (Accepting any equally short move without that direction would loop forever: shown by the mutation runs.) The check that undoes an equally short move whose recomputed length has drifted past the tolerance is a safety net for this argument; realistic coordinates cannot trigger it, and no test covers it (removing it breaks no test). No cap on the number of stops: 500 stops take well under a second. | Spec 5.5 names the method; scan order and acceptance rule are implementation choices. | Proposed |
| D-36 | ~~The heuristic guarantees the tie rule only for nearest-neighbour ties and for the two directions of a round trip, and 2-opt never moves to an equally short order.~~ | Against D-28: 2-opt could leave an equally short order that keeps the input sequence better one move away (stores at the same spot were visited against the input order in 3 of the first 4 random instances checked). | **Withdrawn** (stage 2, third round); replaced by D-38 |
| D-37 | **The 12-stop fixture uses 4 fictional stores** (`FICTIONAL_STORES` in `tests/fixtures/route.ts`, names marked `(fictional)`), added to the 8 real stores because the catalog has only 8. Their positions were picked by a seeded search so that 2-opt clearly beats nearest neighbour in both modes (by 5.06 km round trip, 4.75 km one way). They exist only in test fixtures, not in `data/`. | A fixture where 2-opt changes nothing would not show that 2-opt works. | Proposed |
| D-38 | **How the heuristic applies the tie rule (D-28).** Whenever the heuristic compares two complete orders and they are equally short (within 1e-9 km, D-29), it keeps the one that keeps the input sequence (the earlier one in lexicographic order of input positions): (1) in 2-opt, an equally short reversal is applied when it makes the order earlier (the reversed run puts an earlier input stop at its first position), so the two directions of a round trip, stores at the same spot, and equally short variants one reversal away all resolve towards the input sequence; (2) at the end, if the **input order itself** is equally short, the input order is returned. The tests check all three properties on every heuristic result they make. **Limit**: with more than 8 stops the planner cannot see every equally short order. Finding the earliest of them is as hard as finding the shortest route, which is why the spec only asks for an exact search up to 8 stops. So the result is the input-earliest among the orders the heuristic reaches, not always among all orders. Measured on 200 shuffled 10-stop lines (round trip, 512 equally short out-and-back orders each): every result is one of the shortest and keeps the input sequence at least as well as either straight direction; 92 of 200 are the earliest of all 512 (reproduce with `npx tsx tests/manual/route-line-ties.ts`). Up to 8 stops the exact search applies the rule over all orders. | Applies the confirmed rule of D-28 to the heuristic without inventing a different notion of tie; the limit is stated, not hidden. | Proposed (applies a Confirmed rule; the limit needs your acknowledgement) |

## Purchase optimisation (`src/utils/optimizer.ts`), stage 4

Spec: TECH_SPEC 5.4 and 9, the doc comment of `optimizePurchase` and the `ShoppingPlan` /
`OptimizationResult` docs in `src/models`. Tests: `src/utils/__tests__/optimizer.test.ts`. First
round: free travel only (no home location).

| Id | Decision | Why | Status |
|---|---|---|---|
| D-47 | **Search and ranking.** Every subset of 1..`maxStores` stores is visited (at most 2^8 - 1 = 255 for 8 stores). For a subset, each priceable line goes to the subset's cheapest seller (ties: the earlier store in `stores`), stores that buy nothing drop out. Candidates are ranked on integers (cents): fewest unavailable lines, lowest grand total, fewest stores used, then "earliest stores in input order", read as the used stores' input positions compared one by one (first difference decides: positions 0, 2 beat 1, 2). **Why it is exact:** with free travel the cost of a plan is a sum over lines, so for a fixed set of stores the per-line cheapest choice is the best possible assignment for that set, and it also buys every line the set can buy. Any plan whatsoever uses some set U of at most `maxStores` stores; the subset U is visited, and its plan is at least as good on every ranking criterion (no more unavailable lines, no higher total, and its stores are a subset of U). So the best visited plan is the best of all plans. Checked against an exhaustive search over every assignment of lines to stores on 400 random instances. | Spec 5.4 ("searches every subset of up to `maxStores` stores"); totals in cents make ties exact. | Proposed |
| D-48 | **`maxStores`**: rounded down, then clamped to 1..number of stores (spec: clamped). So 2.9 means 2, 0 and negatives mean 1, `Infinity` means all stores. The API validates integers before calling. | Proposed |
| D-49 | **Order in a plan without a route**: `storeIds` and `stores` in the input order of `stores`; lines within a store, and `unavailableKeys`, in basket order. With a home location, `storeIds` and `stores` follow the route (`route.stops` order). | Deterministic; the model says "in route order when a route exists". | Proposed |
| D-50 | ~~A home location throws `not implemented`.~~ | Stop-gap for the first round of stage 4. | **Superseded** by D-54 to D-56 (stage 4, second round) |
| D-51 | **`savingsVsSingleStore` can be negative**: it is `cheapestSingleStore.grandTotal - bestPlan.grandTotal`, as specified, and when no single store sells everything the best plan can buy *more* items for more money (milk at A for 1.00; caviar only at B for 100.00: single store A 1.00, best plan A + B 101.00, savings -100.00). | Literal spec and model; the ranking puts "fewest unavailable" before price. ## Gaps at the end of API round 8

Checked against TECH_SPEC 6 and `src/services/api.ts` (33 endpoints) with the server's route table.

- **Built, as specified**: health, auth (3), lists (5), items (3), bulk, import; conventions of 6.1
  (statuses, JSON errors, token rules, password rules, emails, zod, Postgres errors never 500,
  malformed path ids 404, parameterised SQL, no per-row queries).
- **Built, different from the letter of the spec, confirmed**: the API match threshold 0.51 (D-18);
  a rename resets unit and quantity (D-136); imports without a written unit get the product's unit
  (D-147, scope creep); 413/415 outside the spec's status list (D-112); the 72-byte password maximum
  (D-120).
- **Built, deferred on purpose**: household visibility for lists and items (TECH_SPEC 6.3, "a user
  sees a list when they own it or belong to its household"), and the member rules (rename and edit
  items allowed; delete and `householdId` change 403). Owner-only until sharing (D-125).
- **Not built**: 20 endpoints (MANUAL_TESTING M30.2), `generateDealNotifications`,
  `server/src/index.ts` and `staticDir` (TECH_SPEC 6.2; `npm start` / `npm run dev` fail until then).

**Uncertain, worth a look** (besides the 41 API decisions still "Proposed"):

- `.env.example` sets `JWT_SECRET=change-me`, which the README's quick start copies. The D-122
  warning only fires for the built-in fallback, so a server started that way signs tokens with a
  publicly known secret **without a warning**. Option: warn for `change-me` too.
- Email case-insensitivity rests on every writer storing lower-case (API and seed do); the database
  does not enforce it (no `lower(email)` index, since the schema is fixed; D-118).
- "Explicit unit is kept" is implemented as kept **in canonical spelling** (`KG` becomes `kg`,
  D-139), and bulk accepts items without a unit although `ParsedItem.unit` is required (D-144).
- An import with one bad line is refused whole (D-146); skipping the bad line was rejected but not
  confirmed.
- Open items from earlier stages that the next endpoints depend on: D-46 (stale deals, for
  `GET /deals`), D-27 (negative savings when no store is complete, for comparison), D-101 (`seed`
  idempotence versus `sync_runs`), D-133 (client stubs).
